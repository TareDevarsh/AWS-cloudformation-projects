# Conventions

Rules every project follows so the repo reads the same everywhere.

[← Portfolio](../README.md)

## Folder naming

- `NN-short-name/` at the repo root (no `projects/` wrapper, so each project is one click from the top of the GitHub page). The two-digit number sets reading order (`01-key-value-store`, `02-ad-creative-scorer`).
- Lowercase, hyphen-separated.

## Creating a project

```bash
./scripts/new-project.sh <NN> <slug> "<Title>"
```

This copies `_template/` and replaces the `{{NN}}`, `{{slug}}`, and `{{Title}}` placeholders. The template deploys as-is (one SSM parameter placeholder), so you can test the pipeline before adding real resources.

## Project layout

This follows the common AWS sample layout (code in `src/`, tests in `tests/`, IaC separate from code), with plain CloudFormation in place of SAM/CDK.

```text
NN-short-name/
├── README.md                  ← what / why / how, start here
├── docs/
│   ├── architecture.md        ← components, data model, decisions
│   ├── workflow.md            ← sequence + state diagrams, deploy lifecycle
│   ├── diagram.py             ← diagram-as-code with AWS icons
│   └── images/architecture.png  ← generated by diagram.py, committed
├── infrastructure/            ← CloudFormation YAML (one or more stacks)
├── src/                       ← Lambda code; one folder per function if >1
├── tests/
│   └── integration/           ← end-to-end tests (sigv4.py helper included)
└── scripts/                   ← deploy.sh, destroy.sh (+ extra ops scripts)
```

## Project README section order

1. **Title + badges + nav bar.** Use shields.io badges for status, IaC, auth, and language, then a link bar: `← Portfolio · Architecture · Workflows · Template · Code`.
2. **Architecture image.** `docs/images/architecture.png` (AWS icons).
3. **Summary.** One paragraph plus a key-facts table (status, services, auth, IaC, idle cost).
4. **Architecture.** A Mermaid flowchart of the same system (renders as text, diff-able).
5. **How it works.** Numbered request flow plus an API table.
6. **Repo layout.** A `text` tree with a `←` note per file.
7. **Deploy / Test / Teardown.** Copy-paste commands.
8. **Cost & security notes.**
9. **What I learned / next steps.** A checklist.

Long reference content (full API examples, schemas) goes in `<details><summary>…</summary>` blocks so the page stays skimmable.

## Diagrams

| What | Tool | Why |
|------|------|-----|
| System architecture (hero image) | [`diagrams`](https://diagrams.mingrammer.com/) Python lib → PNG | Official AWS icons; recognisable at a glance |
| Architecture / stack dependencies | Mermaid `flowchart` | Renders on GitHub, lives in the markdown |
| Request flows | Mermaid `sequenceDiagram` | Shows who calls whom, in order |
| Lifecycles, Step Functions | Mermaid `stateDiagram-v2` | Mirrors states and transitions |
| Data model | Mermaid `erDiagram` or a table | Keys, indexes, attributes |
| Folder layout | `text` code block tree | Plain and copyable |
| Navigation | Markdown links | Mermaid node links are unreliable on GitHub |

Regenerate images after architecture changes: `pip install diagrams && brew install graphviz && python3 docs/diagram.py`.

Not used: Mermaid `architecture-beta` (GitHub doesn't load icon packs, so icons show as `?`) and Mermaid `click` links (GitHub's sandbox blocks plain clicks).

## CloudFormation

- YAML. Use one stack per project unless layers deploy on different cadences (then number the files `01-…`, `02-…` and deploy in order).
- Lambda code is referenced as `Code: ../src/...` and uploaded with `aws cloudformation package` to a private artifact bucket. Add a `cfn-lint` Metadata ignore for `W3002` on those functions.
- Use parameters for anything environment-specific (`Stage`/`Environment`).
- Tag everything with `Project` plus `Stage`/`Environment`.
- Add outputs for every value a script or reviewer needs (endpoints, table names, client policy ARN).
- Validate before deploy: `cfn-lint infrastructure/*.yaml` (must exit 0) and `aws cloudformation validate-template`.

## Security defaults

- APIs use `AWS_IAM` (SigV4) on every method. Ship a client managed policy granting `execute-api:Invoke` on the stage. API keys are not authentication.
- Integration tests assert that an unsigned request gets `403`.
- IAM roles are least-privilege: one role per function, scoped to the project's resources. Allow `Resource: "*"` only where the API requires it, with a comment saying why.
- Storage is encrypted at rest. S3 Block Public Access stays on. No `Principal: "*"` Allow statements. No `0.0.0.0/0` ingress to data stores.
- No secrets in the repo. Use Secrets Manager or SSM Parameter Store.

## Git

- One repo. Each project is a folder, with no nested git repos.
- Commit generated architecture PNGs. Never commit `build/`, packaged templates, `.env`, or credentials (see `.gitignore`).
